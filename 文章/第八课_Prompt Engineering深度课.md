## 一、一个你觉得夸张的实验

同一份数据，同一个问题，两个 Prompt，输出天差地别。

### Prompt A（随便写）

```
分析这份销售数据
（后面跟着一堆 CSV 行）
```

**AI 输出**：

> 从数据来看，整体销售情况一般，有些产品卖得好，有些产品卖得不好。建议优化产品结构，提高利润率。具体可以根据品类进一步细分分析。

一堆正确的废话。没有任何数字，没有任何 actionable insight。

### Prompt B（结构化）

```
你是一个资深电商数据分析师，10年经验。

请分析以下销售数据，严格按照以下格式输出：

1. 核心指标（总销售额、总订单数、平均客单价）
2. 销量 TOP 3 品类（名称+销量+占比）
3. 销量 BOTTOM 3 品类（名称+销量+原因推测）
4. 异常发现（环比波动超过30%的产品，逐一说明）
5. 一句话结论（不超过20字）
6. 改进建议（3条，每条不超过30字）

如果某个分析因数据不足无法完成，请明确说「数据不足，无法分析」，不要猜测。
```

**AI 输出**：

> **1. 核心指标**
> - 总销售额：¥128,450
> - 总订单数：2,847 单
> - 平均客单价：¥45.12
>
> **2. 销量 TOP 3**
> - 手机壳：892 件（31.3%）
> - 充电宝：534 件（18.8%）
> - 数据线：412 件（14.5%）
>
> **3. 销量 BOTTOM 3**
> - 蓝牙键盘：23 件（0.8%）— 推测：客单价偏高（¥299），目标人群窄
> - 屏幕清洁剂：45 件（1.6%）— 推测：刚需性弱，用户倾向于买手机壳时顺带
> - 车载支架：67 件（2.4%）— 推测：季节性产品，当前非出行旺季
>
> **4. 异常发现**
> - 充电宝环比下降 37%：上周促销结束后的正常回落，但连跌两周需关注竞品动作
> - 手机壳环比增长 22%：新款 iPhone 发布效应，预计持续 2-3 周
>
> **5. 一句话结论**
> **促销结束充电宝骤降，新机带动手机壳小高峰。**
>
> **6. 改进建议**
> ① 充电宝做限时秒杀挽回销量
> ② 蓝牙键盘搭配手机壳做组合套餐
> ③ 提前备货车载支架应对下月出行季

**同一个问题，同一个 AI，输出质量差了 10 倍。**

区别在哪？不是 Prompt B 更长，而是 Prompt B **有结构。**

## 二、Prompt Engineering 到底是什么

别被 "Engineering" 吓到。Prompt Engineering 说白了就是 **「怎么跟 AI 说话能让它听懂」。**

就像你不会对一个新同事说「帮我做一下」，你会说「帮我把上周的销售数据拉出来，按品类汇总，做成折线图，下午三点前发我邮箱」。

对人也一样，对 AI 也一样。说清楚了，结果就好。

### 📐 三层框架

每个好 Prompt 都有三层结构，缺一不可：

```
┌─────────────────────────────┐
│  第一层：角色设定 (ROLE)      │  ← 你是什么身份？
│  "你是一个___，负责___"       │
├─────────────────────────────┤
│  第二层：任务描述 (TASK)      │  ← 要做什么？
│  "请帮我___，条件是___"       │
├─────────────────────────────┤
│  第三层：输出格式 (FORMAT)    │  ← 做成什么样？
│  "按以下格式输出：1... 2..."  │
└─────────────────────────────┘
```

**每一层具体写什么：**

| 层级 | 要写的内容 | 反例 | 正例 |
|------|-----------|------|------|
| 角色 | 身份+经验+领域 | "你是个助手" | "你是10年经验的Oracle DBA，擅长SQL调优" |
| 任务 | 做什么+有什么条件+边界 | "帮我写SQL" | "查询2024年Q3销售额TOP 10的产品。字段：产品名、销售额、同比。不要用窗口函数，数据库是Oracle 11g。" |
| 格式 | 输出什么+怎么组织+禁止什么 | (不写) | "用表格展示，每行一个产品。如果某个产品数据缺失，标注'无数据'而不是跳过。" |

**三层中漏了任何一层，输出质量都会打折。**

## 三、三个核心技巧

框架是骨架，技巧是血肉。这三个技巧你在前七课里都见过，但可能没意识到它们是「技巧」。

### 技巧一：Few-shot —— 给 AI 看两个例子

大模型最擅长模仿。你给它看两个例子，它照着写——比你描述一百句都管用。

```python
# ❌ 只描述
prompt = "把自然语言转成SQL"

# ✅ 给例子
prompt = """把自然语言转成SQL。数据库：MySQL 8.0

示例1：
输入：查询销售额大于1000的产品
输出：SELECT product_name, SUM(amount) as total FROM sales WHERE amount > 1000 GROUP BY product_name;

示例2：
输入：查询张三的订单
输出：SELECT * FROM orders WHERE customer_name = '张三' ORDER BY order_date DESC;

现在轮到你了：
输入：查询上个月销量最高的5个品类，按销量降序排列
输出："""
```

**Few-shot 的核心原则**：
- 2~3 个例子最佳，多了浪费 token，少了不稳定
- 例子之间要有差异——覆盖不同场景，AI 才能学到规律
- 例子格式要和期望输出完全一致——不要前面用 Markdown，后面让 AI 输出 JSON

### 技巧二：Chain-of-Thought —— 让 AI「说出思考过程」

人遇到难题会自言自语「如果这样……那应该……」——这叫有声思维。AI 也可以用同样的方式提高准确率。

```python
# ❌ 直接让 AI 出答案
prompt = "12件产品，每件15元，买3送1，买12件要花多少钱？"

# ✅ 让 AI 写思考过程
prompt = """12件产品，每件15元，买3送1，买12件要花多少钱？

请按以下步骤思考：
步骤1：明确规则（买几送几）
步骤2：计算能送多少
步骤3：计算实际需要支付的数量
步骤4：计算总价
步骤5：验证答案

一步步写出你的推理过程，最后给出答案。"""
```

**没有 CoT 的 AI**：「买12件送4件，需要付8件的钱，8×15=120元。」（❌ 错了，买3送1，12件送的是3件不是4件）

**有 CoT 的 AI**：「规则是每买3件送1件。12÷3=4，但因为最后3件不够又凑一组，实际计算：买9件送3件，还剩3件单独买没有送。所以支付9+3-3=0……等等我再算算。买12件，每3件送1件，12÷3=4组，送4件。实际支付12-4=8件。8×15=120元。」（还是这个答案，但 AI 自己在纠正）

> 💡 **注意**：CoT 对 DeepSeek 这种推理模型效果特别好。openai 的 o 系列模型自带推理，不需要手动 CoT。

### 技巧三：结构化输出 —— 让 AI 返回 JSON

前六课我们都是手动解析 AI 的文本回复。但如果你需要程序化处理 AI 的输出（比如前端展示、存入数据库），**直接让 AI 返回 JSON** 是最稳的。

```python
prompt = """分析以下销售数据，按 JSON 格式返回：

{
  "summary": {
    "total_sales": 数字,
    "total_orders": 数字,
    "avg_order_value": 数字
  },
  "top_products": [
    {"name": "产品名", "sales": 数字, "share": "百分比字符串"}
  ],
  "anomalies": [
    {"product": "产品名", "change": "变化描述", "reason": "原因"}
  ],
  "recommendation": "一句话建议，不超过30字"
}

只返回 JSON，不要任何解释性文字。确保 JSON 格式正确，可以被 json.loads() 直接解析。"""
```

然后代码里直接 `json.loads(response)` 就能拿到结构化数据。

| 场景 | 推荐格式 | 原因 |
|------|---------|------|
| 数据分析报告 | JSON + Markdown 混合 | JSON 给程序用，Markdown 给人看 |
| SQL 生成 | 纯文本 | SQL 不是 JSON 的子集 |
| 代码审查 | Markdown 代码块 | 兼容性好，拷贝方便 |
| 前端展示 | 纯 JSON | 前端直接 `JSON.parse()` |

## 四、三个实战场景（复用前七课代码）

理论讲完了，现在拿前七课的真实代码来「手术」。每一个都是改一行 Prompt，效果翻倍。

### 场景一：SQL 生成（对应第一课）

**原来的 Prompt**（第一课 `sql_assistant.py`）：

```python
messages = [{"role": "user", "content": f"根据以下表结构生成SQL：{schema}\n问题：{question}"}]
```

**优化后**：

```python
prompt = f"""你是资深 Oracle DBA，10年经验，擅长复杂 SQL 和性能调优。

根据以下表结构生成 SQL 语句。

表结构：
{schema}

用户问题：{question}

## 输出要求
1. 只输出 SQL 语句，放在 ```sql 代码块中
2. SQL 下方用一行注释简要说明逻辑（不超过30字）
3. 如果问题描述不清晰，先列出你需要澄清的点，不要直接写 SQL

## 示例
问题：查询销售额前10的产品
输出：
```sql
SELECT product_name, SUM(amount) as total_sales
FROM sales
WHERE order_date >= DATE '2024-01-01'
GROUP BY product_name
ORDER BY total_sales DESC
FETCH FIRST 10 ROWS ONLY;
```
-- 按产品汇总2024年销售，降序取前10
"""
```

**改了三个地方**：
- 角色明确到「Oracle DBA」，避免生成 MySQL 语法
- 加了 `FETCH FIRST 10 ROWS ONLY` 的示例（Oracle 12c+ 语法）
- 加了「描述不清先反问」的兜底逻辑

### 场景二：数据分析（对应第七课）

**原来的 Prompt**（第七课 `ai_data_analyst.py`）：

```python
prompt = f"你是一个数据分析师。以下是数据的统计摘要：{summary}\n请分析。"
```

**优化后**：

```python
prompt = f"""你是资深电商数据分析师，8年经验，擅长从数据中发现业务洞察。

请基于以下数据摘要进行分析。

## 数据摘要
{summary}

前20行样本：
{sample}

## 分析框架（必须覆盖，缺数据的标注「数据不足」）
1. **核心指标**：总销售额、总订单数、客单价、同比变化
2. **品类分析**：TOP 3 和 BOTTOM 3（名称+销量+占总体百分比）
3. **趋势洞察**：是否有明显的增长或下降趋势？
4. **异常标记**：环比波动超过 20% 的数据点，逐一说明可能原因
5. **业务建议**：基于数据给出 3 条 actionable 的建议（每条不超过30字）

## 输出格式
- 使用数字序号分段
- 数字类指标必须标注单位（元/件/%）
- 不确定的推断请用「推测」「可能」「疑似」等措辞
- 不要使用「整体表现良好」等模糊表述

现在请开始分析："""
```

**核心改动**：从「请分析」变成了「按框架分析」→ AI 不会自由发挥了。

### 场景三：Agent 工具选择（对应第五课）

**原来的 System Prompt**（第五课 `agent_demo.py`）：

```python
system_prompt = "你是一个智能助手，可以调用以下工具：query_db, search_kb"
```

**优化后**：

```python
system_prompt = """你是一个智能数据助手，可以调用以下工具解决问题。

## 可用工具
1. query_db(sql) - 执行 SQL 查询，返回数据库结果
2. search_kb(query) - 搜索知识库文档，返回相关段落

## 决策规则（严格遵守）
- 涉及「查询」「统计」「销量」「订单」等数据类问题 → 先用 query_db
- 涉及「规定」「流程」「制度」「怎么报销」等文档类问题 → 先用 search_kb
- 如果 query_db 无结果，自动尝试 search_kb
- 如果 search_kb 无结果，诚实告知用户并建议补充文档
- 多步问题按逻辑顺序依次调用，不可跳过中间结果

## 输出要求
- 最终答案用中文，简洁明了
- 引用数据时标注来源（数据库 or 知识库）
- 如果有不确定的地方，标注「未确认」

现在开始处理用户的问题。"""
```

**核心改动**：从「可以调用」变成了「优先级+兜底+输出规范」，Agent 不再随机选工具。

## 五、你手上的 Prompt 工具箱

学到这里，你应该有一个「Prompt 优化 checklist」，每次写 Prompt 之前看一眼：

```
☐ 第一层 · 角色设定：我是谁？有什么经验？擅长什么领域？
☐ 第二层 · 任务描述：做什么？有什么约束？边界在哪？
☐ 第三层 · 输出格式：怎么组织？禁止什么？不确定怎么办？
☐ 进阶 · Few-shot：要不要给 2~3 个例子？
☐ 进阶 · CoT：要不要让它一步步推？
☐ 进阶 · JSON：要不要结构化输出？
```

**不需要每次都全打勾，但前三层永远是底线。**

### 学了 Prompt Engineering 之后，回头看前七课

| 课次 | 原来的 Prompt | 优化后能提升的点 |
|------|-------------|-----------------|
| 第一课 | `"帮我生成SQL"` | 加角色（Oracle/MySQL），加表结构格式 |
| 第二课 | `"你可以调用函数"` | 加工具选择规则，加兜底策略 |
| 第三课 | `"回答以下问题"` | 加引用来源要求，加「不确定请直说」 |
| 第四课 | `RetrievalQA 默认 prompt` | 自定义 prompt 模板，加格式要求 |
| 第五课 | `"你可以用这些工具"` | 加决策规则，加优先级，加多步协调 |
| 第六课 | 继承各模块 prompt | 统一 System Prompt，统一输出格式 |
| 第七课 | `"请分析数据"` | 加分析框架，加必覆盖指标，加不确定标注 |

**优化一遍前七课的 Prompt，整体效果会上一个大台阶。**

## 六、完整代码：Prompt 对比测试器

下面这个工具让你直观感受不同 Prompt 的差异——**同一个问题，三个 Prompt 同时跑，输出并列对比。**

```python
"""prompt_compare.py —— Prompt 对比测试器"""
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("DEEPSEEK_API_KEY", "你的Key"),
    base_url="https://api.deepseek.com"
)

question = "查询每个产品类别的总销售额，按销售额降序排列"
table_schema = "sales(product_name, category, amount, order_date)"

prompts = {
    "❌ 随便写": f"写个SQL查询：{question}。表结构：{table_schema}",

    "✅ 有角色": f"你是资深 SQL 工程师。写个SQL查询：{question}。表：{table_schema}",

    "⭐ 完整三层+示例": f"""你是10年经验的Oracle DBA，擅长复杂SQL和性能优化。

根据以下表结构生成SQL：
{table_schema}

问题：{question}

示例：
输入：查询2024年每个月的订单数
输出：
```sql
SELECT TO_CHAR(order_date, 'YYYY-MM') as month, COUNT(*) as order_count
FROM orders
WHERE order_date >= DATE '2024-01-01'
GROUP BY TO_CHAR(order_date, 'YYYY-MM')
ORDER BY month;
```

现在输出你的SQL，只输出SQL和一行简短注释："""
}

print(f"问题：{question}\n")
for name, prompt in prompts.items():
    resp = client.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.3
    )
    print(f"{'='*50}")
    print(f"{name}")
    print(f"{'='*50}")
    print(resp.choices[0].message.content)
    print()

# 在第八课代码中运行：python prompt_compare.py
```

跑一遍你就会发现——**不是 AI 不行，是你之前给的 Prompt 太随便了。**

## 七、常见 Prompt 误区

| 误区 | 为什么是坑 | 正解 |
|------|-----------|------|
| 「请帮我优化这段代码」 | 优化什么？性能？可读性？安全？ | 说清楚优化目标：减少时间复杂度到 O(n) |
| 一次性塞太多需求 | AI 会顾不过来找，漏掉约束 | 复杂任务拆成多步，每步一个 Prompt |
| 用否定句式描述需求 | 「不要用窗口函数」不如「用子查询实现」 | 说你要什么，而不是你不要什么 |
| 频繁改 System Prompt | 每次调用都改角色，AI 没有一致性 | 同一会话保持 System Prompt 不变 |
| 期待一次完美 | Prompt Engineering 是迭代过程 | 先跑 → 看结果 → 调整 → 再跑 |

## 八、总结

Prompt Engineering **不是玄学，是结构化的沟通方法论。**

| 学到的 | 一句话 |
|--------|--------|
| 三层框架 | 角色 + 任务 + 格式，缺一不可 |
| Few-shot | 给 2~3 个例子，比描述 100 句都有用 |
| Chain-of-Thought | 让 AI「边说边想」，准确率明显提升 |
| 结构化输出 | 需要程序处理就让 AI 返回 JSON |
| 迭代思维 | 先跑 → 看结果 → 调整 Prompt → 再跑 |

```

```
